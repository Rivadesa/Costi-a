# Native transition instructions

Read root instructions, ADR-008/009, docs/native/D1-postgres-api.md and docs/native/D1.2-desktop.md. The approved native transition is .NET/PostgreSQL/WPF plus Vue/TypeScript mobile clients. Legacy Laravel/Tauri must remain unchanged and must never write concurrently into this isolated native database.

D1.2 adds a real WPF client, a typed HTTP library and four authenticated read endpoints. Operational DTOs/configuration contain no money. Checkout is separate and server-authorized, including read APIs and main-only UI. Never treat a client profile as authorization or accept client prices for normal catalogue sales. Keep service, occupancy and settlement independent.

D1 restrictions remain: isolated *_d1_lab/*_d1_test database, loopback HTTP, explicit random role keys, no production identities/device pairing or complete allergy handling. Normal startup never migrates or seeds. No migration of real data is implied. PRs #19–#22 are integrated in `develop` (merge `0ae4e71`); root `AGENTS.md` and `docs/STATUS.md` describe both stacks, with the legacy runtime frozen.

Compile the desktop and run tests/Costina.ClientChecks and tests/Costina.DesktopChecks on Windows; the latter instantiates a real window but does not claim a live end-to-end backend service. Run prior D0 acceptance, snapshot tests and HTTP tests including desktop_reads.py against PostgreSQL. Every write retains audit/outbox/idempotency in one transaction.

D2 (docs/native/D2-realtime.md, issue #24) adds a supervised outbox publisher and a SignalR channel at /api/native/v1/events. Notices are thin (id/type/aggregate/timestamp), never payload or money; account.*/payment.* types reach only main-role connections; delivery is at-least-once and consumers only trigger the same idempotent authoritative HTTP re-read, mandatory after every reconnection. Never put state, prices or kitchen-delivery confirmation into the channel, and keep manual refresh as the fallback. Run tests/Costina.RealtimeChecks against PostgreSQL with the real server binary.

D3.1 (docs/native/D3.1-mvvm-affordances.md): every read DTO carries server-computed allowed actions, filtered per role to mirror the middleware; /session lists global actions. Affordances are never persisted (snapshot payloads stay byte-identical) and idempotent command responses never include them. The WPF client is MVVM (CommunityToolkit.Mvvm) and enablement is a pure mapping of those lists: never re-derive business rules in a client, and never advertise an action a role would get 403 for.

D3.2 (docs/native/D3.2-guest-restrictions.md): guest restrictions are structured (guest position or whole table, kind, substance, severity — never free notes, never color-only) and every preparation projects its applicable ones at read time. A change while courses are active sets restrictionsPendingAck and blocks fire-next/ready/serve with restrictions_unacknowledged until kitchen (or main) acknowledges; station marks stay allowed. Snapshot fields are additive; pre-D3.2 payloads restore empty.

D3.5 (docs/native/D3.5-restriction-review.md, issue #36 / finding F05): a restriction change with sent work flags `reviewPending` on every SENT preparation it applies to; kitchen (or main) must decide per preparation with `review-preparation` (`unaffected` / `adapt` / `remake`, note mandatory). Any pending review blocks `ready`/`serve` of that course and `fire-next` with `restrictions_unreviewed`; `remake` returns the preparation to Fired and withdraws the course validation. `restrictionsPendingAck` is derived; `acknowledge-restrictions` no longer exists. Snapshot fields are additive; a D3.2 payload with the global flag restores with every sent preparation pending. Never reintroduce a global "seen" acknowledgement.

D3.6 (docs/native/D3.6-account-reopen-refund.md, issue #37 / finding F07): "paid" and "closed" differ; a closed account is reopened with `reopen` (main only, reason mandatory, audited) and accepts changes again; `refund` (main only) returns existing credit only and never deletes a payment (`paidCents` is net, `refundedCents`/`refunds` additive). Waiters add extras through `POST /services/{id}/commands/add-consumption` (main/service, dining `expectedVersion`, catalogue price, money-free response, `account_closed` when closed); the account itself is managed only from the main terminal (`/checkout/...`). Never expose amounts on the waiter path.

D3.3 (docs/native/D3.3-durable-pending.md): the uncertain command is persisted through IPendingStore BEFORE the first attempt (DPAPI CurrentUser on Windows, access key never stored) and cleared only on success or explicit application rejection; on reconnect it is restored and blocks new mutations until the identical retry. Forced shutdown no longer loses the pending state; it is still exactly ONE uncertain command per client, not an offline work queue. No Windows/PostgreSQL automatic installer claims. Publish the entire self-contained directory, not the executable alone. Record exact CI commit, verified artifacts and physical testing separately. #17 remains open until actual legacy migration/integration.

D3.4 (docs/native/D3.4-client-hardening.md, review findings F01–F04/F08): a WPF command is built only from a `Context` — the entity read correctly whose identity matches the selected row; changing the selection invalidates the previous detail and a failed read leaves nothing actionable. `IPendingStore.Load()` returns Absent/Restored/Unreadable/Unavailable; the last two BLOCK new mutations (fail closed) and the file is never deleted: reconcile through `GET /commands/{key}` (same actor only, returns the stored response) and quarantine (`*.cuarentena-*`) instead of destroying evidence; `Clear(key)` only removes the file carrying that confirmed key. The durable file is isolated per installation (`/session.installationId`, table `native_d1.installation`, run init-lab once more) + scope hash + role + slot, with an inter-process lock per live window; a pending from another installation is reported, never resent. The server echoes `Idempotency-Key` on every response; the client treats a 403/404/409/422 as definitive only with a recognisable JSON `error` that is not `storage_conflict`/`idempotency_conflict`/`operation_unconfirmed` AND the echoed key matches. Package version `0.7.0-d3.4` lives in the csproj files and feeds `/health`, `/session.serverVersion` and the CI manifest.

D4.1–D4.3b (docs/native/D4.1-users-sessions.md, D4.2-device-pairing.md, D4.3a-station-authz.md, D4.3b-wpf-login.md; issue #26 / finding F06) supersede the "explicit random role keys" of D1: `COSTINA_KEY_*` no longer authenticates anything. Every request enters with a user session (PBKDF2 password, users created only through `create-user` with the password on stdin, sliding 30 min token with a 14 h cap, hashes only at rest) or a paired device (`dev.<id>.<secret>`, one-time 5 min code approved by main with role and station, secret delivered once, revocation aborts live SignalR connections). The station narrows and never widens the role: a kitchen device only marks its own station and `ready`/`review-preparation` require station `pase`; affordances mirror it. Browsers reach the hub only with the one-use 60 s ticket from `POST /auth/hub-token`, accepted as `?access_token=` on the hub route alone and never logged. The audit actor is the real identity (`user:<name>` / `device:<name>`). In the WPF client the password never goes through bindings or disk, the session token lives in memory only (best-effort logout on disconnect), the device token is stored with DPAPI per port and cleared on 401, and identity operations use `ApiClient.PostRawAsync` — the uncertain-command machinery (D3.3/D3.4, still isolated per installation/scope/role/slot and fail-closed) is reserved for domain commands. Test suites provision `lab-<role>` users with the environment of the started server, use their own scope and send `Idempotency-Key` on every POST. Never reintroduce shared keys, default credentials or tokens in URLs outside the hub ticket.

D5.1 (docs/native/D5.1-packaging-base.md, ADR-011, issue #27) opens milestone 4. PostgreSQL roles are separate: the superuser is used only by `provision`; `costina_owner` owns database and schema and is used only by `init`/`upgrade`/`init-lab` (its credentials in `config/owner.json` are never read by a normal start); the running engine uses `costina_runtime`, which has no DDL, no DELETE and cannot rewrite `commands`/`audit` — **every new table or new write path must be added to `grants.sql`**, and CI runs the whole HTTP battery and RealtimeChecks with that role, so a missing grant fails loudly. Lifecycle is explicit (`provision` → `init` → `create-user` → start; `upgrade` is the only schema change on an existing installation; a normal start never migrates or seeds). `COSTINA_MODE=installation` refuses an over-privileged runtime connection and refuses `init-lab`; the laboratory keeps `COSTINA_LAB_MODE=true`. Mutable state lives under the data root (`%ProgramData%\Costina` or `COSTINA_DATA`), never in the program directory; settings come from `config/server.json` with environment variables on top. `packaging_http.py` must stay the FIRST HTTP suite: it provisions the CI database and exports the role connections. Planned cuts: D5.2 Windows service, D5.3 LAN HTTPS with a local CA, D5.4 backup/restore, D5.5 installer, D5.6 physical script.

D5.2 (docs/native/D5.2-windows-service.md) registers the engine as the Windows service `Costina` with `install-service` (elevated, once): virtual account `NT SERVICE\Costina`, delayed automatic start with no user session, SCM recovery, quoted image path, optional dependency on the PostgreSQL service. The configuration ACL gives that account read access to `config/server.json` only — never widen it to `owner.json`. `uninstall-service` never touches the data root. In installation mode the engine logs to `<data root>/logs` (exception type only, never messages, bodies, tokens or connection strings) and `Microsoft.AspNetCore` request lines stay filtered at Warning because the query string carries the hub ticket: do not re-enable them. `GET /diagnostics` is main-only and must stay free of business data, money, paths and secrets. The `windows-service` CI job exercises a real SCM service on the runner's native PostgreSQL (`tests/service/service_checks.ps1`).

D5.3 (docs/native/D5.3-lan-https.md) opens the LAN over HTTPS only. Plain HTTP stays on loopback forever; the LAN listener exists only in installation mode with a certificate from `provision-tls`, issued by a per-installation local CA whose **critical name constraints** limit it to the server names given at creation and private IPv4 ranges — never issue an unconstrained CA, never replace an existing CA silently (`renew-tls` reissues the server certificate and leaves devices untouched), and never let the service account read `tls/ca.key` (it reads `tls/server.pfx` only). Clients must validate the chain normally: never add a TLS validation bypass, and the WPF client accepts only `http://127.0.0.1:PORT` or `https://NAME:PORT`. The firewall rule opens the HTTPS port on private/domain profiles only. Login and pairing claims are throttled per origin and target (10 failures / 5 min → 429 for 60 s) on top of the generic response and delay. `packaging_http.py` validates the chain with OpenSSL and proves the name constraints; the `windows-service` job validates it with SChannel through the real service.

D5.4 (docs/native/D5.4-backup-restore.md): the service takes an unattended daily backup in installation mode (`pg_dump` custom format of schema `native_d1` with the RUNTIME role inside an exported snapshot; credentials through the child environment, never arguments). Each backup has a `.json` manifest with SHA-256 and a per-table content digest computed in the same snapshot (`BackupDigest`). `restore <file>` uses the owner role, refuses a damaged file, a different scope or an installation that already has data (it never overwrites), and must re-verify every table digest before declaring success — never weaken it to a row count or to "pg_restore exited 0". Backups are sensitive (credential hashes): keep them ACL-restricted and out of logs. A new table is covered automatically (tables come from the catalog) but still needs its `grants.sql` entry. `COSTINA_PG_BIN` must point at PostgreSQL tools of the server's major version; CI installs client 17 for that reason.

D5.5 (docs/native/D5.5-installer.md, `deploy/windows/`): the NSIS installer only copies files and calls engine commands — keep ALL logic in `Costina.Server.exe` (`setup-server`, `stop-services`, `remove-server`, `first-user`), where CI exercises it. `setup-server` on an empty data root creates its own PostgreSQL cluster under `<data root>/pg` (loopback only, scram, own port 5544, service `CostinaPostgres` as NetworkService), then provision → init (or verified `restore` with `COSTINA_RESTORE_FILE`) → provision-tls → install-service; on an existing data root it re-registers services, takes a BACKUP and only then runs `upgrade`. A failed fresh setup removes only what that run created; nothing ever deletes an existing data root, and uninstalling never touches `%ProgramData%\Costina`. The bootstrap superuser password is generated, used once and never stored. The first administrator is created interactively with a hidden password (`first-user`); the installer never sees a password. Additional workstations trust the server CA only if it is a Costina CA with critical name constraints (`import-ca.ps1`). The PostgreSQL archive version is pinned in `package.ps1`; pin its SHA-256 too. The installer is unsigned until #12. The `Native Windows installer` workflow installs the real package in all three modes.

D5.6 (docs/native/D5.6-physical-install.md) closes milestone 4 in code; issue #27 is closed only with the promoter's filled result table from that physical script — never on a green CI alone. `load-demo` (installer `/DEMO=1`) loads the fictitious fixtures explicitly, with the owner role and only into an EMPTY configuration; it flags the installation as a demo (`demo` in `/health` and `/session`, banner in the WPF status) through the fixtures' own idempotent command row, so the flag travels with backups and needs no schema. Never load fixtures implicitly, never hide the demo flag, and never treat a demo installation as a base for real data; `init-lab` stays laboratory-only. `status` is a read-only, credential-free, secret-free summary (services, /health, certificate expiry, CA fingerprint, last backup, second destination) that exits 1 when the engine does not answer: keep it free of secrets and business data.

CI artifacts: GitHub's artifact storage quota was exhausted on 2026-09-21 (every push uploaded ~250 MB with 14-day retention) and turned EVERY job red at its upload step, including untouched workflows. Rules since then: binaries are uploaded once (the engine only from the desktop workflow and inside the installer — never again from `windows-compile`), binary retention is 3 days (installer 5), small evidence keeps 14, and every `upload-artifact` step is `continue-on-error: true` because tests decide whether a cut passes, not storage. When reading CI, tell a quota failure (`Failed to CreateArtifact`) from a real one before touching code. Any HTTP suite query that reads shared tables must filter by its own scope: other suites (and the demo fixtures of `packaging_http.py`) live in the same CI database.

D6.1 (docs/native/D6.1-pwa-base.md, issue #28) starts the operational PWA in `frontend/pwa` (Vue 3 + TypeScript + Vite; runtime dependency: `vue` only — adding one needs a reason). The engine hosts its build at `/app/` on the SAME origin (`PwaHosting`): never open CORS, never serve anything but build files anonymously, and keep the strict CSP free of `unsafe-inline`/`unsafe-eval`/third parties (so no inline scripts or styles in the PWA). Workflows and `package.ps1` must build the PWA BEFORE the engine. The PWA is operational-only (ADR-007): it authenticates as a paired DEVICE, never a person; every API response goes through `money-guard.ts` and any money-looking key rejects the whole response; waiter-facing reads use their own projections (`GET /catalog` has no prices — never reuse `/checkout/*`). The service worker caches the shell under `/app/` only and must never touch `/api/`; no Background Sync. Data age is always visible and the UI never shows remembered operational state as current. The pairing code may arrive in the URL fragment (`#pair=`), validated by a closed regex and removed after use; keep handling `hashchange`. Test pyramid: vitest (runs locally with Node), `pwa_http.py`, and Playwright against the real engine in CI (`COSTINA_E2E=1`), which also asserts zero money keys in every JSON the browser receives and zero CSP violations. Agreed for D6.3: ONE durable uncertain command (like the WPF), not a multi-command queue, because domain commands carry `expectedVersion`.

D6.2 (docs/native/D6.2-pwa-waiter-read.md): the PWA waiter board is read-only and server-untouched. Realtime follows the D2 contract exactly: the channel only NOTIFIES (notice content is deliberately ignored), every notice and — mandatorily — every reconnection trigger the same authoritative HTTP re-read, bursts are coalesced, and the UI states its link honestly (live / reconnecting / polling) with the age of the last read always visible; on a server outage it keeps the last data, says it may be stale and never refreshes the read time. Browsers connect to the hub with a FRESH single-use hub ticket per connection and reconnection (`accessTokenFactory`), WebSockets only with `skipNegotiation` (one request = one ticket); the device token must never appear in a URL. A hub start that neither connects nor fails degrades to polling after 10 s. `live.ts` has no DOM and is unit-tested with a fake hub; `e2e/board.spec.ts` drives a real browser against the real engine. Second and last planned runtime dependency of the PWA: `@microsoft/signalr`. Restriction and review labels always spell out kind, substance and severity — never colour alone.

D6.3 (docs/native/D6.3-pwa-durable-command.md): the PWA has exactly ONE durable uncertain command (IndexedDB), mirroring D3.3/D3.4 — never turn it into a multi-command offline queue: domain commands carry `expectedVersion`. Invariants of `commands.ts`: persist BEFORE the first attempt and never send what could not be persisted; block every other mutation while it exists; retry resends the identical bytes and key; close the uncertainty ONLY on a success whose echoed `Idempotency-Key` matches or on a definitive rejection (403/404/409/422 + recognisable JSON `error` not in storage_conflict/idempotency_conflict/operation_unconfirmed + echoed key); a 401 does NOT close it; a command from another installation or an unreadable one is never resent; `clear(key)` removes only the command carrying that key. UI enablement is a pure mapping of server affordances (already filtered by role and station); the only local checks are input format. Automatic retry happens in the foreground only, after a successful authoritative read. `window.fetch` must be called WITHOUT a receiver (a method call throws Illegal invocation in browsers — there is a regression test). The waiter-route response of `add-consumption` names its reference `consumptionId` (it was `chargeId`, which the PWA money guard rightly refused, leaving an applied command unconfirmed): never put checkout vocabulary (charge, payment, balance…) in a key of any response a service/kitchen device can receive — `pwa_http.py` checks it with the PWA's own rule. A success with a matching echo CLOSES the uncertainty first and only then is refused for money content. E2E proves 'one effect' by the service version rising exactly by one after a genuinely lost response (`route.fetch()` + `route.abort()`).

D6.4 (docs/native/D6.4-pwa-kds.md): the PWA kitchen screen is per station and server-untouched. A station sees the WHOLE fired/preparing course, with other stations' work dimmed, labelled and button-less; `pase` (and a kitchen device without a station) sees every station plus READY courses until served, and is the only place for `ready` and `review-preparation` (unaffected/adapt/remake, note mandatory). Every button exists only because the server announces that action on THAT preparation or course (affordances already filtered by role and station): `kitchen.ts` decides what is painted and what is dimmed, never what is allowed — do not re-derive the station matrix in the client, and keep the server as the boundary (the E2E proves `wrong_station` with the device's own token). `review-preparation` is advertised on the PREPARATION, so the station mirror in `Affordances.StationKeeps` filters it there (pass only) — when the domain adds an item-level action, mirror its station rule at item level, and cover it in `station_http.py`. Restriction warnings are never dimmed and always spell kind, substance and severity. Comandero and kitchen share `operations.ts` (live board + the ONE durable uncertain command) and `StatusPanel.vue`: a new operational screen must reuse them, never reimplement realtime or pending handling. E2E specs own their table: board=M6, commands=M7, kitchen=M8, pwa_http=M2.

D6.5 (docs/native/D6.5-qr-install-physical.md) closes milestone 5 in code; issue #28 is closed only with the promoter's filled result table from that physical script (Android + iPad) — never on a green CI alone. The WPF Puestos tab shows the pairing code as a QR of `https://HOST:PORT/app/#pair=CODE` (`PairingLink` in Costina.Client; QRCoder renders it as an in-memory PNG, no System.Drawing). The QR carries ONLY the one-use 5-minute code, in the FRAGMENT — never a token, never a credential, never anything the closed code alphabet rejects — and scanning approves nothing: the administrator still approves with role and station. The host comes from the address the WPF itself uses when it is already on the LAN; on loopback the administrator types the device address (same D5.3 rule without the loopback exception, remembered per machine) and without a valid one there is NO QR and the screen says why. The PWA has no scanner of its own: keep `Permissions-Policy: camera=()`. Installability: PNG icons 192/512 + maskable 512 in the manifest and a 180 px opaque `apple-touch-icon` (iOS ignores manifest icons and SVG), generated by `frontend/pwa/scripts/make-icons.mjs` and versioned; everything stays under `/app/` on the same origin. The PWA project has no `@types/node`: tests that need Node declare what they use in `tests/node-shim.d.ts`.
