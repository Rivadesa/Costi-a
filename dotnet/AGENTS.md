# Native transition instructions

Read root instructions, ADR-008/009, docs/native/D1-postgres-api.md and docs/native/D1.2-desktop.md. The approved native transition is .NET/PostgreSQL/WPF plus Vue/TypeScript mobile clients. Legacy Laravel/Tauri must remain unchanged and must never write concurrently into this isolated native database.

D1.2 adds a real WPF client, a typed HTTP library and four authenticated read endpoints. Operational DTOs/configuration contain no money. Checkout is separate and server-authorized, including read APIs and main-only UI. Never treat a client profile as authorization or accept client prices for normal catalogue sales. Keep service, occupancy and settlement independent.

D1 restrictions remain: isolated *_d1_lab/*_d1_test database, loopback HTTP, explicit random role keys, no production identities/device pairing or complete allergy handling. Normal startup never migrates or seeds. No migration of real data is implied. PRs #19–#22 are integrated in `develop` (merge `0ae4e71`); root `AGENTS.md` and `docs/STATUS.md` describe both stacks, with the legacy runtime frozen.

Compile the desktop and run tests/Costina.ClientChecks and tests/Costina.DesktopChecks on Windows; the latter instantiates a real window but does not claim a live end-to-end backend service. Run prior D0 acceptance, snapshot tests and HTTP tests including desktop_reads.py against PostgreSQL. Every write retains audit/outbox/idempotency in one transaction.

D2 (docs/native/D2-realtime.md, issue #24) adds a supervised outbox publisher and a SignalR channel at /api/native/v1/events. Notices are thin (id/type/aggregate/timestamp), never payload or money; account.*/payment.* types reach only main-role connections; delivery is at-least-once and consumers only trigger the same idempotent authoritative HTTP re-read, mandatory after every reconnection. Never put state, prices or kitchen-delivery confirmation into the channel, and keep manual refresh as the fallback. Run tests/Costina.RealtimeChecks against PostgreSQL with the real server binary.

D3.1 (docs/native/D3.1-mvvm-affordances.md): every read DTO carries server-computed allowed actions, filtered per role to mirror the middleware; /session lists global actions. Affordances are never persisted (snapshot payloads stay byte-identical) and idempotent command responses never include them. The WPF client is MVVM (CommunityToolkit.Mvvm) and enablement is a pure mapping of those lists: never re-derive business rules in a client, and never advertise an action a role would get 403 for.

D3.2 (docs/native/D3.2-guest-restrictions.md): guest restrictions are structured (guest position or whole table, kind, substance, severity — never free notes, never color-only) and every preparation projects its applicable ones at read time. A change while courses are active sets restrictionsPendingAck and blocks fire-next/ready/serve with restrictions_unacknowledged until kitchen (or main) acknowledges; station marks stay allowed. Snapshot fields are additive; pre-D3.2 payloads restore empty.

D3.5 (docs/native/D3.5-restriction-review.md, issue #36 / finding F05): a restriction change with sent work flags `reviewPending` on every SENT preparation it applies to; kitchen (or main) must decide per preparation with `review-preparation` (`unaffected` / `adapt` / `remake`, note mandatory). Any pending review blocks `ready`/`serve` of that course and `fire-next` with `restrictions_unreviewed`; `remake` returns the preparation to Fired and withdraws the course validation. `restrictionsPendingAck` is derived; `acknowledge-restrictions` no longer exists. Snapshot fields are additive; a D3.2 payload with the global flag restores with every sent preparation pending. Never reintroduce a global "seen" acknowledgement.

D3.6 (docs/native/D3.6-account-reopen-refund.md, issue #37 / finding F07): "paid" and "closed" differ; a closed account is reopened with `reopen` (main only, reason mandatory, audited) and accepts changes again; `refund` (main only) returns existing credit only and never deletes a payment (`paidCents` is net, `refundedCents`/`refunds` additive). Waiters add extras through `POST /services/{id}/commands/add-consumption` (main/service, dining `expectedVersion`, catalogue price, money-free response, `account_closed` when closed); the account itself is managed only from the main terminal (`/checkout/...`). Never expose amounts on the waiter path.

D3.3 (docs/native/D3.3-durable-pending.md): the uncertain command is persisted through IPendingStore BEFORE the first attempt (DPAPI CurrentUser on Windows, access key never stored) and cleared only on success or explicit application rejection; on reconnect it is restored and blocks new mutations until the identical retry. Forced shutdown no longer loses the pending state; it is still exactly ONE uncertain command per client, not an offline work queue. No Windows/PostgreSQL automatic installer claims. Publish the entire self-contained directory, not the executable alone. Record exact CI commit, verified artifacts and physical testing separately. #17 remains open until actual legacy migration/integration.

D3.4 (docs/native/D3.4-client-hardening.md, review findings F01–F04/F08): a WPF command is built only from a `Context` — the entity read correctly whose identity matches the selected row; changing the selection invalidates the previous detail and a failed read leaves nothing actionable. `IPendingStore.Load()` returns Absent/Restored/Unreadable/Unavailable; the last two BLOCK new mutations (fail closed) and the file is never deleted: reconcile through `GET /commands/{key}` (same actor only, returns the stored response) and quarantine (`*.cuarentena-*`) instead of destroying evidence; `Clear(key)` only removes the file carrying that confirmed key. The durable file is isolated per installation (`/session.installationId`, table `native_d1.installation`, run init-lab once more) + scope hash + role + slot, with an inter-process lock per live window; a pending from another installation is reported, never resent. The server echoes `Idempotency-Key` on every response; the client treats a 403/404/409/422 as definitive only with a recognisable JSON `error` that is not `storage_conflict`/`idempotency_conflict`/`operation_unconfirmed` AND the echoed key matches. Package version `0.7.0-d3.4` lives in the csproj files and feeds `/health`, `/session.serverVersion` and the CI manifest.

D4.1–D4.3b (docs/native/D4.1-users-sessions.md, D4.2-device-pairing.md, D4.3a-station-authz.md, D4.3b-wpf-login.md; issue #26 / finding F06) supersede the "explicit random role keys" of D1: `COSTINA_KEY_*` no longer authenticates anything. Every request enters with a user session (PBKDF2 password, users created only through `create-user` with the password on stdin, sliding 30 min token with a 14 h cap, hashes only at rest) or a paired device (`dev.<id>.<secret>`, one-time 5 min code approved by main with role and station, secret delivered once, revocation aborts live SignalR connections). The station narrows and never widens the role: a kitchen device only marks its own station and `ready`/`review-preparation` require station `pase`; affordances mirror it. Browsers reach the hub only with the one-use 60 s ticket from `POST /auth/hub-token`, accepted as `?access_token=` on the hub route alone and never logged. The audit actor is the real identity (`user:<name>` / `device:<name>`). In the WPF client the password never goes through bindings or disk, the session token lives in memory only (best-effort logout on disconnect), the device token is stored with DPAPI per port and cleared on 401, and identity operations use `ApiClient.PostRawAsync` — the uncertain-command machinery (D3.3/D3.4, still isolated per installation/scope/role/slot and fail-closed) is reserved for domain commands. Test suites provision `lab-<role>` users with the environment of the started server, use their own scope and send `Idempotency-Key` on every POST. Never reintroduce shared keys, default credentials or tokens in URLs outside the hub ticket.

D5.1 (docs/native/D5.1-packaging-base.md, ADR-011, issue #27) opens milestone 4. PostgreSQL roles are separate: the superuser is used only by `provision`; `costina_owner` owns database and schema and is used only by `init`/`upgrade`/`init-lab` (its credentials in `config/owner.json` are never read by a normal start); the running engine uses `costina_runtime`, which has no DDL, no DELETE and cannot rewrite `commands`/`audit` — **every new table or new write path must be added to `grants.sql`**, and CI runs the whole HTTP battery and RealtimeChecks with that role, so a missing grant fails loudly. Lifecycle is explicit (`provision` → `init` → `create-user` → start; `upgrade` is the only schema change on an existing installation; a normal start never migrates or seeds). `COSTINA_MODE=installation` refuses an over-privileged runtime connection and refuses `init-lab`; the laboratory keeps `COSTINA_LAB_MODE=true`. Mutable state lives under the data root (`%ProgramData%\Costina` or `COSTINA_DATA`), never in the program directory; settings come from `config/server.json` with environment variables on top. `packaging_http.py` must stay the FIRST HTTP suite: it provisions the CI database and exports the role connections. Planned cuts: D5.2 Windows service, D5.3 LAN HTTPS with a local CA, D5.4 backup/restore, D5.5 installer, D5.6 physical script.

D5.2 (docs/native/D5.2-windows-service.md) registers the engine as the Windows service `Costina` with `install-service` (elevated, once): virtual account `NT SERVICE\Costina`, delayed automatic start with no user session, SCM recovery, quoted image path, optional dependency on the PostgreSQL service. The configuration ACL gives that account read access to `config/server.json` only — never widen it to `owner.json`. `uninstall-service` never touches the data root. In installation mode the engine logs to `<data root>/logs` (exception type only, never messages, bodies, tokens or connection strings) and `Microsoft.AspNetCore` request lines stay filtered at Warning because the query string carries the hub ticket: do not re-enable them. `GET /diagnostics` is main-only and must stay free of business data, money, paths and secrets. The `windows-service` CI job exercises a real SCM service on the runner's native PostgreSQL (`tests/service/service_checks.ps1`).
