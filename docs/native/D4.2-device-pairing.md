# D4.2 — Dispositivos emparejados por código de un solo uso

Fecha: 2026-09-17. Rama `feat/d4.2-device-pairing` sobre `develop` (`c1e3c7c`, PR #40). Segundo corte de la issue #26 (hallazgo F06). Consultar el CI de la PR para resultados ejecutados.

## Qué cambia

- **Dispositivo = identidad separada del usuario** (tablas relacionales `native_d1.devices` y `native_d1.pairings`, aditivas: repetir `init-lab` una vez en bases existentes).
- **Flujo de emparejamiento** en `/api/native/v1/auth/…`:
  1. Un `main` emite un código (`POST /auth/pairings`): **un solo uso**, caducidad de **5 minutos**. El QR lo pintará el cliente (D4.3); el servidor entrega el contenido.
  2. El dispositivo, **sin credenciales aún**, lo reclama (`POST /auth/pairings/claim` con su nombre) y recibe un secreto de recogida. El reuso o la caducidad responden un genérico `invalid_code` con freno de 400 ms; el un-solo-uso lo garantiza la transición de estado en base, no el cliente.
  3. Un `main` ve los pendientes (`GET /auth/pairings/pending`) y **aprueba asignando rol y estación** (`POST /auth/pairings/{id}/approve`) o deniega (`/deny`).
  4. El dispositivo recoge sus credenciales (`POST /auth/pairings/{id}/collect`): el secreto viaja **una única vez** (transición `approved→consumed`); mientras no hay decisión responde `pending`, y si fue denegado, `denied` sin crear nada.
- **Autenticación de dispositivo**: bearer `dev.<id>.<secreto>`. Actor de auditoría `device:<nombre>`; `/session` expone `station`. En reposo **solo hashes** (código, secreto de recogida y secreto del dispositivo).
- **Revocación** (`POST /auth/devices/{id}/revoke`, solo main, con quién revocó registrado): corta HTTP en el acto y **aborta las conexiones SignalR vivas** del dispositivo mediante el registro de conexiones del hub. `GET /auth/devices` lista dispositivos con su estado.

## Qué NO cambia

Las claves de laboratorio y las sesiones de usuario de D4.1 siguen funcionando (las claves se retiran en D4.3). La **estación se registra y expone pero aún no restringe permisos** — esa matriz rol×estación es D4.3. Dominio, comandos y frontera económica intactos. El cliente WPF no cambia (la interfaz de emparejamiento llega en D4.3); el contrato queda probado por HTTP. Loopback (LAN/TLS es #27).

## Comprobaciones automáticas

- HTTP (`pairing_http.py`, ámbito propio, 7 tests): flujo completo con entrega única del secreto; el token de dispositivo autentica con rol/estación/actor y sin acceso a caja; códigos de un solo uso, caducados e inválidos con respuesta genérica; gestión solo para `main` (403 al dispositivo de sala); denegación sin crear dispositivo; revocación inmediata e idempotente-honesta (segundo revoke 404); solo hashes en reposo.
- RealtimeChecks **B6** (procesos reales): alta de usuario por CLI, login, emparejamiento completo por HTTP, suscripción SignalR con el token del dispositivo que **recibe avisos**, y revocación que **aborta la conexión viva** (observado como cierre sin reintentos) y deja el token rechazado con 401.

## Guion de prueba manual (Windows)

Con el laboratorio `.lab` y binarios de esta PR (**repetir `init-lab` una vez**):

1. Crear un usuario main (`create-user jefe main`, contraseña por stdin) y hacer login con curl para obtener token.
2. `POST /auth/pairings` con ese token: anotar `code` (esto será el QR).
3. Desde "otro dispositivo" (curl sin credenciales): `claim` con el código y un nombre → guarda `pairingId` y `pollSecret`. Repetir el claim con el mismo código: rechazo genérico.
4. `collect` antes de aprobar → `pending`. Aprobar desde el token main con rol `service` y estación `sala-1`. `collect` de nuevo → llega `deviceToken` una sola vez (repetir collect → 404).
5. `GET /session` con el `deviceToken`: rol `service`, actor `device:<nombre>`, `station` `sala-1`. `GET /checkout/accounts` → 403.
6. Revocar el dispositivo desde main → `GET /session` con el deviceToken pasa a 401 al instante. Esperar >5 min con un código sin usar y comprobar que caduca.

## Límites

La aprobación exige rol `main` (el concepto "administrador" como rol separado se decidirá si hace falta al retirar las claves en D4.3). Sin límite de emparejamientos simultáneos ni expiración de dispositivos por inactividad. La estación aún no restringe nada. El freno anti-fuerza-bruta sigue siendo mínimo y por petición.
