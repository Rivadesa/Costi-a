# D4.3b — Login de usuario y emparejamiento del puesto en el cliente Windows

Fecha: 2026-09-17. Rama `feat/d4.3b-wpf-login` sobre `develop` (`5e75d46`, PR #42). Cierre en código de la issue #26 (hallazgo F06). Consultar el CI de la PR para resultados ejecutados.

## Qué cambia

- **Entrada por usuario y contraseña** (PC principal o cualquier puesto con persona): `AuthClient` anónimo en la biblioteca de cliente hace el login; la contraseña no pasa por bindings ni toca disco; el **token de sesión solo vive en memoria** y al desconectar se intenta el logout (mejor esfuerzo). El estado de conexión muestra el actor real y, si procede, la estación.
- **Puesto emparejado**: el token `dev.*` del dispositivo se guarda **cifrado con DPAPI** por puerto (mismo criterio que la orden incierta: fichero ilegible en claro; corrupto se descarta y borra; un 401 al conectar limpia el emparejamiento revocado y lo dice claro). Botón "Conectar puesto emparejado" cuando existe credencial.
- **Emparejar desde la propia pantalla de conexión**: código + nombre del puesto → solicitud → sondeo de aprobación cada 2 s mientras el código vive → guardado DPAPI y conexión automática. Mensajes explícitos para denegado, caducado o sin respuesta.
- **Pestaña "Puestos"** (solo rol main; el servidor lo impone además por permisos): generar el código de un solo uso (texto grande para teclear o copiar — el **QR visual llegará con la PWA #28**, que es quien lo escaneará), aprobar/denegar solicitudes asignando rol y estación, y revocar puestos con expulsión inmediata (también del tiempo real).
- `ApiClient.PostRawAsync`: POST autenticado directo para operaciones de identidad — la maquinaria de orden incierta queda reservada a comandos de dominio, que es donde tiene sentido.

## Qué NO cambia

Servidor intacto (todo el contrato es el de D4.1–D4.3a). Dominio, comandos, realtime y frontera económica. La cola durable de la orden incierta funciona igual con cualquier tipo de credencial. Loopback (LAN/TLS es #27).

## Comprobaciones automáticas

- ClientChecks: login con parseo y error genérico de credenciales; collect distinguiendo pendiente/denegado/aprobado con el token una sola vez; `PostRawAsync` sin tocar la orden incierta.
- DesktopChecks (Windows real): credencial del puesto con round-trip DPAPI, fichero ilegible en claro y corrupto descartado y borrado; más los checks de arranque y mapeo de siempre.
- El flujo servidor equivalente ya quedó probado extremo a extremo en D4.2/D4.3a (`pairing_http.py`, `station_http.py`, RealtimeChecks B6).

## Guion de prueba manual (Windows) — cierre del Hito 3

Con el laboratorio `.lab` y binarios de esta PR (repetir `init-lab`; quitar las `COSTINA_KEY_*` del `.cmd`; crear el primer usuario: `server\Costina.Server.exe create-user jefe main`):

1. Cliente 1: entrar como `jefe`. El estado muestra `user:jefe · rol main`. Aparecen las pestañas Puestos y Cuenta/Caja.
2. En Puestos: generar código. Cliente 2 (sin credenciales): "Emparejar este puesto" con el código y nombre `tablet-sala`; en el cliente 1 aprobar como Sala / `sala-1`. El cliente 2 se conecta solo y muestra `device:tablet-sala · estación sala-1`; no ve Cuenta/Caja ni Puestos.
3. Cerrar el cliente 2 y reabrirlo: "Conectar puesto emparejado" entra sin teclear nada (la credencial está cifrada en el perfil del usuario).
4. Emparejar un cliente 3 como Cocina / `cold`: solo puede marcar elaboraciones frías y no puede validar el pase; emparejado como `pase`, sí.
5. Desde el cliente 1, revocar `tablet-sala`: el cliente 2 pierde el tiempo real en el acto y al reconectar se le indica que debe emparejarse de nuevo.
6. Login con contraseña incorrecta: error genérico y sin pistas. Comprobar que `%LOCALAPPDATA%\Costina\` no contiene nada legible.

## Límites

Sin cambio de contraseña ni gestión de usuarios por interfaz (alta por CLI hasta que #27 lo automatice). El sondeo de aprobación es del cliente (2 s); sin notificación push al puesto. El QR visual queda para la PWA. El rol "administrador" sigue siendo el rol main.
