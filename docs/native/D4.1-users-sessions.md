# D4.1 — Usuarios con contraseña y sesiones con token de corta vida

Fecha: 2026-09-17. Rama `feat/d4.1-users-sessions` sobre D3.6 (`d054caf`, PR #39). Primer corte de la issue #26 (hallazgo F06). Consultar el CI de la PR para resultados ejecutados.

## Qué cambia

- **Identidad relacional** (decisión de persistencia del promotor: nunca JSONB): tablas `native_d1.users` (usuario en minúsculas, hash de contraseña, rol main/sala/cocina, activo) y `native_d1.sessions` (hash del token, caducidad deslizante, tope absoluto, revocación). Aditivas e idempotentes: añadirlas a una base existente = repetir `init-lab` una vez.
- **Contraseñas**: PBKDF2-SHA256, 210.000 iteraciones, sal de 16 bytes, comparación de tiempo constante; ante un usuario inexistente se verifica contra un hash señuelo para no filtrar existencia por tiempo. Mínimo 12 caracteres. Alta explícita por CLI: `Costina.Server.exe create-user <usuario> <rol>` con la contraseña por **stdin** (nunca argumento, variable de entorno, eco ni log). Sin credenciales por defecto.
- **Sesiones**: `POST /api/native/v1/auth/login` (anónimo; respuesta genérica `invalid_credentials` con freno de 400 ms ante fallo) emite un token aleatorio de 256 bits que **solo viaja una vez**; en la base queda su SHA-256. Caducidad deslizante de 30 min renovada en cada petición autenticada, con tope absoluto de 14 h (un turno largo, no un día). `POST /auth/logout` revoca la sesión actual. Revocación también por desactivación del usuario.
- **Middleware**: primero intenta la sesión de usuario; si no, cae a las claves de laboratorio `COSTINA_KEY_*`, que **siguen funcionando hasta D4.3** (transición sin ruptura para laboratorio, WPF y suites). El **actor de auditoría** pasa a ser la persona real (`user:maitre`) cuando hay sesión; `/session` lo expone como `actor`.

## Qué NO cambia

Dominio, comandos, realtime y frontera económica intactos. El cliente WPF sigue entrando con clave de laboratorio (el login de usuario en la interfaz llega en D4.3, junto a la retirada de las claves). Sin dispositivos ni estaciones (D4.2/D4.3). Loopback se mantiene (LAN/TLS es #27). El freno de login es mínimo y por petición: no es una defensa completa de fuerza bruta (se endurecerá con el emparejamiento de dispositivos).

## Comprobaciones automáticas

- PersistenceChecks (puras): el hash no contiene la contraseña, verificación correcta/incorrecta, formato corrupto falla cerrado, la sal hace único cada hash.
- HTTP (`identity_http.py`, ámbito propio): login y `/session` con actor real conviviendo con las claves de laboratorio; fallo genérico sin token; CLI rechaza contraseñas cortas y roles desconocidos; el rol del token lo impone el servidor (sala sin caja); renovación deslizante verificada en base y tope absoluto que gana; caducidad, logout y desactivación revocan; en reposo solo hashes (ni token ni contraseña aparecen).

## Guion de prueba manual (Windows)

Con el laboratorio `.lab` y binarios de esta PR (**repetir `init-lab` una vez** por las tablas nuevas):

1. En una terminal del laboratorio: `server\Costina.Server.exe create-user maitre main` (te pedirá la contraseña por stdin; usa una de 12+). Verificar que ni el comando ni la salida muestran la contraseña.
2. Con curl: login correcto devuelve token; login con contraseña mala devuelve el mismo error genérico tardando ~medio segundo.
3. `GET /session` con el token: `actor` = `user:maitre`. Con la clave de laboratorio de siempre: `actor` = `lab-main` (el cliente WPF sigue funcionando igual).
4. `POST /auth/logout` con el token y repetir `/session`: 401.
5. Reiniciar el motor: un token emitido antes del reinicio sigue valiendo (la sesión está en la base, no en memoria).

## Límites

Sin recuperación de contraseña ni gestión de usuarios por interfaz (alta solo por CLI en este corte). Sin bloqueo de cuenta por intentos. Un usuario = un rol global; la estación llega en D4.2/D4.3. Las claves de laboratorio siguen activas a propósito hasta D4.3.
